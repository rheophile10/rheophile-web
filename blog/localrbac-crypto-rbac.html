Dev log · 2026-07-15

Records that a group can keep, with no single keyholder as a target 🔐

localRbac enforces role-based access control (RBAC) with cryptography only. It uses no server and no network at access time. The data is in a local-first CRDT database that several people run, edit offline, and merge.

RBAC is useful. But RBAC without cryptographic enforcement is a UI that shows a guard but checks nothing. A person who edits the file can bypass that UI. The name for this pattern is "cargo cult".

In localRbac, a person must hold a key to read. A write must have an admin-signed signature, and the merge checks that signature. No one person can decrypt the full dataset alone, because the Shamir method splits the master key k-of-n. Thus no person becomes the target.

Try the 3-user demo → Source code on GitHub
Do not put real secrets in localRbac at this time. It is a proof of concept only. It has no formal security review, no threat assessment, and no authorization to protect real data. The code operates, but it is a demonstration of a design, not a product.

The goal

The goal is that a group keeps its shared records together, as one truth that converges. The group does not trust a server, and its members are often offline. The members know that any one of them can lose a laptop. They also know that a person can coerce any one of them.

Thus the records are in a normal SQLite file that each person carries. Access control is part of the data itself. It must stay in effect when a person copies the file, edits it offline, and merges it. The design has three properties and uses no server:

  • Two or more parties each run the database and edit it offline.
  • Edits merge. Two peers exchange a delta to reconcile. A subgroup converges to a checkpoint that its members agree on.
  • The data does not depend on one keyholder alone. If the group loses one person, or if an attacker coerces one person, the attacker does not receive the data.

The engine is cr-sqlite, a CRDT extension to SQLite. Its merge operates on each column, and the merge is commutative, associative, and idempotent. Thus replicas collaborate on the same records and converge in any merge order. The cr-sqlite extension gives convergence. On top of it, localRbac adds all the rules about who can see and who can change each item.

Read control is a data-encryption key

A person can always read the bytes on their own disk, and you cannot prevent that. Thus the question "Can Alice read this?" becomes "Can Alice decrypt this?" Each resource is a compartment, for example patient:alice or notes. Each resource has its own data-encryption key (DEK), and each DEK has a version. A record is a set of encrypted cells, one cell for each (record, column) pair. The DEK of the resource encrypts each cell: 

cell(pk = rid|resource|col, rid, resource, col, ct, dek_ver, author, sig)

A reader receives the DEK in one of two ways:

  • The admin derives the DEK from one root secret when it is necessary: DEK = HKDF(rootKey, "dek:"+resource, "v"+ver). The engine stores no resource keys.
  • Each other member receives a sealed DEK. For each grant, the admin seals that DEK to the X25519 key of the member and puts it in a keywrap row. Only that member can unseal it.

No online authority is necessary to read. listRecords decrypts each cell if you hold its key, and it skips the other cells. A person without a grant has the same ciphertext and sees a 🔒. Nothing leaks, because there is no plaintext to hide.

Revocation is key rotation. To revoke a user, the admin increases dek_ver and seals the new key to the remaining members. The revoked user keeps the old ciphertext. That user cannot read the data that a member writes after the revocation.

Write control is a signature that the merge checks

Encryption stops reads, but it does not stop writes. Any person can append a row to a file. Thus each row carries the Ed25519 key of its author and a signature. The engine enforces the signature at a point that a person cannot bypass: at merge. The engine replays an incoming changeset into a temporary staging database. Before the engine trusts the changeset, it makes sure that these two conditions are true:

  1. System rows (identities, grants, key-wraps, checkpoints) have a valid signature, and the admin is their author. These rows establish who is a writer.
  2. Data cells have a valid signature, and their author is a current writer for that resource.

The changeset merges only if each row passes. The merge rejects each of these items, and it gives a reason:

  • A forged cell.
  • A person who makes themselves the admin.
  • A reader who tries to write.

Authenticity is a property of each row, not of the envelope. Thus authenticity stays intact through the transitive gossip of cr-sqlite.

Local consensus: two files, one state root

Two peers exchange changesets to reconcile. It is not necessary to send the data to know that the peers converged. Each peer calculates a state root: a SHA-256 hash of the sorted state of the cells and the grants. If the roots are equal, the states are identical. The peers compare 64 hex characters, not a database.

The engine code documents one problem. The db_version of cr-sqlite is a local clock, and a merge assigns it again. Thus "all changes after checkpoint H" uses a local watermark, not a portable version vector.

Group consensus: the wipe-and-rebuild ceremony

A full subgroup converges through a ceremony. A coordinator merges the diffs, records a signed checkpoint, and gives each member a rebuild slice. Then each member wipes the local database and rebuilds it from the slice. Figure 3 shows the sequence.

  • Each diff holds the changes of one member after the last checkpoint.
  • The coordinator can also rotate each DEK. This step is optional.
  • The checkpoint is a hash of the agreed state.
  • The coordinator does not send the merged database back.
  • A rebuild slice holds the auth state and the checkpoint state. It also holds only the non-archived cells that the member has a right to.

This one procedure does three jobs:

  • Compaction.
  • Data minimization: each member receives only the data that the member has a right to.
  • Redistribution from the same checkpoint.

The lock occurs in the evening, and the unlock occurs in the morning.

No single keyholder: Shamir threshold custody

One problem remains: the root secret of the admin can derive each DEK. If any one person can decrypt the full collective dataset alone, that person becomes a target for extortion. Cryptography cannot protect a person against physical force.

Thus localRbac uses Shamir's secret sharing. It splits the custody key into n shares in the field GF(2⁸). Any k shares reconstruct the key. Any k−1 shares reveal nothing. Then localRbac seals each share to the key of one custodian.

sealVault encrypts a payload with a random key and then splits that key. The unlock is a distributed operation. Each custodian seals their share again to the opener. The opener combines k shares.

A 4-of-5 quorum continues to operate if it loses one custodian. To break it, an attacker must compromise four people at the same time. No single keyholder is a point of failure or a point of coercion.

Where the database lives: demand-paged onto encrypted IndexedDB

Ordinary SQLite is demand-paged: its pager reads and writes individual pages (4 KB by default) from the file as queries touch them, holding only a small page cache in RAM — a 50 GB database runs in a few megabytes, and only a :memory: database lives entirely in RAM. Most SQLite-in-the-browser throws that away: sql.js loads the whole file into a Uint8Array on the WASM heap. localRbac keeps the demand-paged model in the browser by injecting a VFS — SQLite's virtual-filesystem seam — so the pager's block reads and writes land in IndexedDB, one page at a time, never the whole file in memory.

The persistent connection opens through EncryptedIDBVFS, a vendored copy of wa-sqlite's IDBBatchAtomicVFS. Each SQLite page becomes an IndexedDB block keyed [path, offset, version], fetched and written on demand, with transparent per-page AES encryption in the VFS layer and batch-atomic commits. The only :memory: database is the throwaway staging connection that authorizes an incoming changeset before it merges (the same staging step from Write control, above) — the store of record is always the encrypted IndexedDB VFS.

Two properties let this run from file://, where most persistent-SQLite options can't: the VFS is Asyncify-based, so it needs no SharedArrayBuffer and therefore none of the COOP/COEP cross-origin-isolation headers that absurd-sql or threaded-OPFS builds require; and the crsqlite.mjs WASM is base64-inlined as a data: URI, so opening the engine costs zero network fetches. Demand-paged, encrypted, offline — from a double-clicked HTML file. (For the bare mechanism — just this VFS, without the encryption or CRDT — see the standalone write-up: Demand-paged SQLite from file://.)

The binary is built here, not installed

The engine underneath is not the published @vlcn.io/wa-sqlite — it is compiled from pinned source by sqlite-wasm-build, using the base variant (cr-sqlite + FTS5), the recipe that reproduces the published package. That matters here more than it would elsewhere, because SQLITE_OMIT_LOAD_EXTENSION is set: nothing can be loaded at runtime, so every capability has to be in the binary. Installing the published build means accepting someone else's answer to "which extensions does this database have" — and for a project whose whole argument is that the rules must survive the file being copied, that is an odd thing to leave to a registry.

Because the variant declares itself under the same package name and exposes the same import specifiers, adopting it moved one line and no source: 

"@vlcn.io/wa-sqlite": "file:../../../sqlite-wasm-build/dist/base"

Swapping in geo (R*Tree, Geopoly) or vec (sqlite-vec) is the same line with a different word — which is the reason for building them as separate variants rather than one everything binary. The build, the four variants and the six toolchain failures behind them are written up in One binary, every extension.

One trap worth repeating. The swap can look like it worked while the registry binary is still the one loading. @vlcn.io/crsqlite-wasm was a dependency nothing imported, and it pulled the published wa-sqlite in transitively — which npm then hoisted over the local file: dependency without a word. Check the bytes, not the lockfile: sha256sum node_modules/@vlcn.io/wa-sqlite/crsqlite.wasm dist/base/crsqlite.wasm.

The parts of the datalayer

The engine is a headless package, and an app connects it to a UI. By design, the engine is resource-agnostic and column-agnostic. Records are a generic entity-attribute-value store. The name "notes" is a convention of the demo on top of that store. These are the parts:

The engine

packages/datalayer/src/engine/crengine.ts

This file holds the full compartmented-RBAC mechanism:

  • genesis (become the admin)
  • grant and revoke
  • putRecord and listRecords
  • importChangeset, with the staging-authorize logic
  • runConsensus and rebuildSliceFor

The essential schema is eight small tables: adminroot, identity, grantrec, dekver, keywrap, cell, archived, and checkpoint. All of them are cr-sqlite CRRs. The exception is a local watermark.

Threshold custody

packages/datalayer/src/vault.ts · crypto/secret-sharing/shamir.ts

sealVault, openVault, and produceContribution do the k-of-n seal and the distributed unlock. The second file holds the Shamir split and the Shamir combine in the field GF(2⁸). tests/{shamir,vault}.test.ts has end-to-end tests for this part.

Consensus and compartments

packages/datalayer/src/consensus/ · compartment/

The consensus folder holds pure functions for the checkpoint chain: tip, chainFrom, isDescendant, and converged. The compartment folder holds the compartment fold. The fold does an LWW merge of the decrypted cells from all the resources that a viewer can read. The two parts have no side effects, and you can test each part independently.

Crypto that you can replace

packages/datalayer/src/crypto/{kdf,signing,sealing,aead,hash,secret-sharing}/

Each cryptographic task is a folder. The index.ts file of the folder selects one implementation. Thus you can replace a protocol with a change to one line. These functions are all native:

  • Signatures: WebCrypto Ed25519
  • Seals: X25519
  • Record encryption: AES-256-GCM
  • Hash and derivation: SHA-256/HKDF

Only two parts use WASM/noble. The first part is the memory-hard keystore KDF (Argon2id, through hash-wasm). The second part is the one sync-critical page cipher. Each WASM blob is inline as base64. Thus there are zero network fetches, and this is also true for file://.

An identity that you hold and the app never stores

packages/datalayer/src/crypto/keystore.ts

An identity is a generated keypair. An Argon2id-encrypted keystore file wraps the keypair. The user downloads this file and keeps it. The app never writes the identity to IndexedDB.

The provision method is a public-key card exchange. You export a self-signed {pub, name, xpub, sig} card, and the admin grants to that key. No private material goes from one person to another person at any time.

The notes demo and the UI

packages/app/src/{notes.ts,ui.ts} · public/demo.html

This is the demo layer. notes.ts holds the full convention: a note is a record with a title and a body in the notes resource. (It is approximately 20 lines.) demo.html shows the built app three times in iframes: as admin, as writer, and as reader. Thus you can see role enforcement, offline edits, and the merge on one screen.

Run the demo

The three-user demo is one HTML file, and the demo page loads it three times. The result is three machines that never communicate. Do these steps:

  1. Grant access to the writer.
  2. Deny access to the reader.
  3. Add a note.
  4. Export a delta.
  5. Import the delta in the adjacent frame.

The note converges, and the reader sees 🔒. All of the demo uses the real engine. The demo simulates only the transport: it sends text between iframes as a replacement for a USB stick.
